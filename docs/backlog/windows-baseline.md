# Backlog - Windows CIS/Microsoft security baseline

Settings from the public CIS (HardeningKitty) and Microsoft Security Compliance Toolkit Windows
baselines that `rules/windows-baseline.yaml` does not emit. The registry settings that the engine can
express are generated; everything below is deferred. Grouped by setting type and reason, with counts.
Generated by scratchpad\Build-BaselineRules.ps1 on 2026-10-21.

## Non-registry setting types - need a protocol/runner the baseline import does not cover

The registry protocol reads values; these setting types read something else, so they wait for the
runner noted against each. Counts are raw baseline rows across all benchmarks (not yet deduped).

- **accesschk** (257 rows) - effective user-rights assignment per host - HardeningKitty reads it with accesschk; the engine reads rights from SYSVOL (gpo/security) not host-effective, so an effective per-host read is not built yet.
- **auditpol** (224 rows) - effective advanced audit policy - needs an audit-policy read per host (auditpol / audit.csv); not built yet.
- **AdvancedAudit** (175 rows) - advanced audit policy subcategories - needs an effective audit-policy read per host; not built yet.
- **PrivilegeRight** (159 rows) - user-rights assignment (SeXxxPrivilege) - needs the GptTmpl/security read per host (SYSVOL via gpo protocol); host-effective rights are not read yet.
- **MpPreferenceAsr** (100 rows) - Defender ASR rules / MpPreference - FEASIBLE later via cim (root/Microsoft/Windows/Defender MSFT_MpPreference); not emitted here.
- **service** (64 rows) - service start type / state - FEASIBLE later via cim (Win32_Service); overlaps the live windows-server / workstations service rules.
- **accountpolicy** (46 rows) - password/lockout account policy - needs the GptTmpl security read per host; not read host-effective yet.
- **SystemAccess** (46 rows) - security-policy System Access block - needs the GptTmpl security read per host; not read host-effective yet.
- **secedit** (33 rows) - secedit/security-template settings - needs the GptTmpl security read per host; not read host-effective yet.
- **localaccount** (9 rows) - local account state (Guest/Administrator) - FEASIBLE later via cim (Win32_UserAccount); overlaps WS-LOCAL-ACCOUNT-WEAK.
- **RegistryList** (5 rows) - registry list/multi-value membership - value names are list entries (often with backslashes); needs a list/subkey read a per-value rule cannot address.
- **ScheduledTask** (1 rows) - scheduled task definition - MSFT_ScheduledTask returns the principal as an embedded instance; not expressible as a flat row yet.

## Registry settings dropped - readable in principle, but not emitted

- value name a rule cannot address (empty, or contains . [ ] { } quote or backslash) - **196 rows**.
- per-user setting (HKCU / HKU<SID>) - the registry runner reads per machine (HKLM) only - **63 rows**.
- operator 'novalues' cannot be mapped to a failure safely - **3 rows**.
- operator 'notcontains' cannot be mapped to a failure safely - **2 rows**.

## OS-split settings emitted as variants - file-level targeting caveat

23 settings have an expected value that genuinely differs between Windows client and
Windows Server (after resolving within-OS benchmark disagreement to each OS's most-frequent value).
Each is emitted as two rules in `windows-baseline.yaml` with distinct ids (`-CLIENT` / `-SERVER`) and
the per-OS value. A Keeper rule carries no per-rule target (only the file-level `targets:`), so both
variants are judged on every Windows host the file resolves: on the wrong OS a variant would misfire.
To make them OS-correct at run time, move each pair into the os-specific packs (`workstations.yaml`,
`windows-server.yaml`) whose file-level target already filters by OS, or add a per-rule target to the
engine. Keeper is not run live against this estate, so the file validates and the variants are kept.
